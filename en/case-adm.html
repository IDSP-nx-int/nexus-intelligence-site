1) Context / Problem

This prototype exists to practice model-driven app design and Dataverse architecture in a realistic domain: procurement and inventory. The goal is to structure an end-to-end process flow (RQ → OC → receiving/stock), with a schema that scales and process enforcement through BPF + approvals.

The focus is not UI polish—it’s repeatable architecture: clean relationships, clear ownership of entities, and workflow gates that reduce ambiguity.

2) Solution (what is implemented)

Core delivered

  • Model-driven app navigation with modules: Almacén, Compras, Proyectos, Catálogos.
  • Dataverse schema with normalized core tables and explicit relationships.
  • BPF for Requisition (RQ): Capture → Approval request → Resolution → Close/fulfillment.
  • BPF for Purchase Order (OC): Capture → Approval request → Resolution → Receiving/Payment.
  • Approval automation via Power Automate (Approvals connector), updating record status.

What this project is optimized for

  • Dataverse table design: lookups, choices, ownership, and consistent naming.
  • Process enforcement: BPF stages + controlled status transitions.
  • Automation wiring: approval requests + update actions + traceability fields.
  • Portfolio-ready evidence: ERD, schema screenshots, BPF diagrams, flow screenshots.

The deliverable is a clean, explainable “systems prototype” that demonstrates architecture—not a production rollout.

3) Architecture

Data model

  • Dataverse-centered schema for procurement + inventory.
  • Core entities cover requisitions, purchase orders, inventory movements, and catalogs.
  • Relationships designed to support reporting and process automation without hardcoding.

Workflow automation

  • BPF defines stage gates and guides user actions.
  • Power Automate approvals orchestrate approve/reject outcomes.
  • Status updates write back to Dataverse records (approved/rejected/pending).

4) Key Features

  • Process-driven UX: users follow the BPF rather than improvising steps.
  • Normalized schema: catalogs (Cliente/Proveedor/Producto/Proyecto) referenced by lookups.
  • Approval outcomes: flow updates status fields to reflect decision (approve/reject/pending).
  • Inventory trace: movements linked back to requisition/purchase-order lines where applicable.
  • Portfolio documentation: ERD + “what exists in the solution” + BPF + flow evidence.

5) Scope snapshot

What’s included

  • Core tables: Clientes, Proveedores, Productos, Proyectos, Requisición, Orden de Compra, Inventario (Mov/Saldos).
  • BPFs: 2 (RQ + OC).
  • Approval flows: 2 (RQ + OC).
  • Navigation: Almacén / Compras / Proyectos / Catálogos.

What’s intentionally not included

  • Dashboards: none (model-driven charts or Power BI).
  • Production hardening: full role matrix, ALM pipelines, monitoring, and load testing are out of scope for this prototype.
  • Extended line-level modules: some “Line/Detail” tables are present but not positioned as core portfolio flow.
